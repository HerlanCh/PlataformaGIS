# ADR-001: Monolito modular con arquitectura hexagonal

## Estado
Aprobado

## Fecha
2026-10-11

## Contexto
El proyecto consiste en una plataforma comunitaria de alerta temprana para La Paz y El Alto, desarrollada como proyecto de grado y operada con un equipo unipersonal sobre niveles gratuitos de infraestructura en la nube. 

Se evaluaron dos alternativas principales de diseño arquitectónico:
1. **Microservicios distribuidos:** Ofrecen aislamiento físico entre dominios, pero introducen una sobrecarga operativa extrema (múltiples pipelines de CI/CD, serialización de red, orquestación de despliegues, consistencia eventual compleja y consumo excesivo de memoria en instancias gratuitas).
2. **Monolito en capas tradicional (capas horizontales API/Servicio/DAO):** Es fácil de arrancar, pero propicia acoplamiento severo entre conceptos, "fugas" de detalles de base de datos a la lógica de negocio y dificulta la extracción o desactivación selectiva de funcionalidades.

## Decisión
Adoptar un **Monolito Modular con Arquitectura Hexagonal (Puertos y Adaptadores)** estructurado como un monorepo pnpm:
- **Aislamiento modular:** Cada funcionalidad del sistema vive en `packages/modules/<nombre>` y cuenta con sus propias capas internas `domain/`, `application/`, `adapters/`, `migrations/`, `tests/` e `index.ts`.
- **Regla de dependencia estricta:** `adapters → application → domain`. El dominio es TypeScript puro sin dependencias de frameworks ni librerías de infraestructura (salvo tipos primitivos de `shared-kernel`).
- **Sin dependencias directas entre módulos:** Ningún módulo puede importar código interno de otro módulo. La comunicación entre módulos se realiza exclusivamente a través de **eventos de integración versionados** despachados sobre un bus de eventos en memoria (o outbox transaccional) o puertos públicos expuestos en `index.ts`.
- **Aislamiento de datos:** Cada módulo gestiona sus propias tablas y migraciones. No existen claves foráneas entre tablas de módulos diferentes en la base de datos.
- **Control de compuertas:** Las restricciones arquitectónicas son verificadas y garantizadas de forma automatizada en el pipeline de CI mediante `dependency-cruiser`.

## Consecuencias

### Positivas
- **Mantenibilidad:** El código de negocio está aislado del framework web (Fastify), del motor de base de datos (PostGIS/Drizzle) y de los protocolos de comunicación (Socket.io/Telegram).
- **Testabilidad:** Se puede probar el 100 % de la lógica de dominio y aplicación en memoria, sin necesidad de levantar bases de datos ni servicios de red para pruebas unitarias.
- **Simplicidad operativa:** Un solo artefacto de despliegue para el backend, reduciendo la fricción en servidores gratuitos como Render o VM Always Free.
- **Flexibilidad por interruptores:** Cada módulo puede habilitarse o desactivarse mediante variables `FEATURE_<MODULO>` sin afectar la compilación.

### Negativas / Mitigaciones
- **Mayor cantidad de código inicial (ceremonia de capas):** Se mitiga mediante un generador de módulos (`pnpm gen:module` con plop) para crear la estructura base en segundos.
- **Curva de disciplina:** Se mitiga imponiendo compuertas automáticas en CI que rechazan cualquier Pull Request con violaciones de dependencias.
