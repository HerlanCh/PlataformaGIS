# ADR-002: Selección del stack tecnológico y estrategia de costo cero

## Estado
Aprobado por el autor del proyecto (2026-10-11)

## Fecha
2026-10-11

## Contexto
La plataforma de alerta temprana requiere alta capacidad de procesamiento geoespacial, tiempo real para alertas ciudadanas, soporte de funcionamiento sin conexión (PWA offline) y un bot de mensajería (Telegram), todo operando bajo una restricción presupuestaria inamovible: **100 % software libre y planes gratuitos (costo operativo cero)**.

Se consideraron las siguientes alternativas técnicas:
1. **Frontend:** Next.js (SSR) frente a React + Vite (PWA SPA). Next.js requiere ejecución de servidor Node.js o Edge Functions que complican el almacenamiento en caché agresivo fuera de línea de service workers y consumen recursos de servidor limitados.
2. **Backend:** Express frente a Fastify. Express carece de validación por esquema nativa y ofrece menor rendimiento de concurrencia.
3. **ORM / Acceso a datos:** Prisma frente a Drizzle ORM. Prisma introduce un motor binario pesado en Rust con soporte espacial PostGIS engorroso y difícil de optimizar.
4. **Base de datos espacial:** MongoDB (GeoJSON básico) frente a PostgreSQL + PostGIS. PostGIS es el estándar mundial en GIS con índices espaciales GiST altamente optimizados y funciones avanzadas (`ST_DWithin`, `ST_SnapToGrid`).

## Decisión
Se define el siguiente stack tecnológico estricto:

1. **Gestión de Monorepo y Lenguaje:**
   - **pnpm workspaces:** Manejo eficiente de dependencias compartidas mediante enlaces duros.
   - **TypeScript estricto (`strict: true`, `noUncheckedIndexedAccess: true`):** En todo el monorepo (API, Web, Bot, Paquetes).

2. **Backend y Contratos:**
   - **Node.js + Fastify:** Alto rendimiento, bajo consumo de memoria y soporte nativo de serialización/validación de esquemas.
   - **Socket.io:** Comunicación en tiempo real con salas basadas en celdas espaciales, recuperación de estado y fallback automático a HTTP polling.
   - **Zod:** Validación de contratos de entrada, generación de esquemas OpenAPI y tipado estático inferido de extremo a extremo.

3. **Base de Datos y Motor Geoespacial:**
   - **PostgreSQL + PostGIS:** Soporte geoespacial nativo, proyecciones geodésicas (SRID 4326) e índices espaciales GiST.
   - **Drizzle ORM + SQL espacial manual:** Migraciones ligeras y transparentes en TypeScript sin cajas negras, permitiendo invocar funciones espaciales directamente sin penalización.

4. **Frontend:**
   - **React + Vite + vite-plugin-pwa:** Aplicación PWA servida como estático en CDN gratuita (Vercel / Cloudflare Pages), con Service Worker y Workbox para almacenamiento en caché y cola de peticiones fuera de línea (`IndexedDB`).
   - **Leaflet + OpenStreetMap + leaflet.heat:** Librería de mapas liviana, sin costos de tokens o claves de API propietarias (evitando Google Maps o Mapbox).

5. **Bot de Mensajería:**
   - **Telegraf:** Framework TypeScript para la API de bots de Telegram; actúa como un adaptador de entrada más al núcleo de la aplicación.
   - _Nota (2026-10-19): descartado por el ADR-004 junto con el canal Telegram._

6. **Herramientas de Calidad y Pruebas:**
   - **Vitest:** Ejecución ultrarrápida de pruebas unitarias y de integración.
   - **Testcontainers:** Pruebas de integración sobre instancias reales de PostGIS en contenedores Docker efímeros.
   - **Playwright:** Pruebas end-to-end de la PWA y validación de escenarios sin conexión.
   - **k6:** Pruebas de carga para certificar los percentiles p95 de latencia.

7. **Infraestructura Gratuita:**
   - Backend en Render (plan gratuito) o VM de Oracle Cloud Always Free.
   - Frontend en Vercel o Cloudflare Pages.
   - Base de datos en Neon o Supabase (capa gratuita con extensión PostGIS activa).

## Consecuencias

### Positivas
- Cero costo recurrente durante todo el desarrollo y fase piloto.
- Compartición del 100 % de contratos y tipos Zod entre backend, frontend y bot.
- Rendimiento óptimo en dispositivos móviles de gama baja gracias al bundle reducido de React+Vite frente a frameworks de servidor más pesados.
- Capacidad nativa de operar sin conexión gracias a la arquitectura PWA estática.

### Negativas / Mitigaciones
- El documento original del proyecto mencionaba Next.js; al cambiar a Vite hay que actualizar la matriz de marco lógico.
- Necesidad de escribir consultas PostGIS manuales (`sql` en Drizzle) para operaciones avanzadas; mitigado mediante un repositorio espacial bien encapsulado en la capa de adaptadores.
